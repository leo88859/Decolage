## 4. Réponses aux points demandés

### (a) Réutilisable pour une boutique
Le modèle « Boutique » existe (`src/data/templates.ts`, premium) : pages accueil/catalogue/panier/commandes, entité Produit (Produit, Prix, Stock, Statut), briques donnees/detail/recherche/auth/admin/export-csv, textes, CGV et feuille de route (tâche `bo-cgv`). Côté écran, l'architecture `co-products`, `co-orders`, `co-sales` (`src/lib/proto-arch.ts`, `codegen/kit-arch.ts`) fournit : liste produits avec stock, création de commande avec décrément de stock (`proto-arch.ts` ~l.280-290), changement de statut, chiffre d'affaires, import CSV. Le panier (`proto-runtime.ts`) ajoute/retire des quantités. `src/lib/appdata.ts` valide déjà `cart` et `orders` (tests).
Tout cela est **simulation côté navigateur** : prix en texte libre (« 18 € »), aucune table produits/commandes, pas de paiement, pas de TVA/livraison/adresse, pas d'e-mails.
Réutilisable côté plateforme : Stripe (checkout/webhook/signature/idempotence, `src/lib/billing.ts`, `stripe-errors.ts`), RLS + tests PGlite, publication (`sites`), validation (`publish.ts`), pages légales et CGV, modèle de migration SQL avec fonction `security definer` (`inscrire`), anti-spam IP + champ piège (`api/waitlist`).

### (b) Base persistante et comptes finaux, ou localStorage ?
- Applications générées/publiées : **localStorage**. La démo publiée `/s/[slug]/app` utilise `persist: true, storeKey: site:<slug>` : données propres à chaque visiteur dans son navigateur, jamais partagées (`proto-runtime.ts`, mode `local`). Sans stockage, mode `none`.
- Projet exporté : `codegen` écrit « les données sont enregistrées dans le navigateur » (commentaire en tête de `codegen/index.ts`). Seule exception : liste d'attente avec Supabase du client (`kit-cloud.ts` : tables `listes`/`inscriptions`, RLS, fonction `inscrire`, connexion/inscription du propriétaire).
- Pas de comptes d'utilisateurs finaux ni de base par application. Les données personnelles « sérieuses » (projets du créateur, profils, sites, inscrits, acceptations) sont dans le Supabase de Décollage lui-même.

### (c) Liste d'attente / formulaire public
- **Réel.** `POST /api/waitlist/[slug]` (formulaire HTML) : valide le slug, champ piège, regex e-mail, limite 8/min/IP (mémoire d'instance, donc contournable en multi-instances), puis `insert` dans `waitlist` via client anon. RLS : insertion publique seulement si le site existe et n'est pas suspendu ; lecture/suppression réservées au propriétaire.
- Honnêteté : le succès est affiché seulement si l'insertion réussit ou si doublon (code 23505, volontairement masqué). Un seul faux succès volontaire : le champ piège renvoie « merci » aux robots. Si le cloud n'est pas configuré → page d'erreur, pas de faux succès.
- Limite : le CSP des sites autorise `form-action 'self'`, aucun e-mail de confirmation, pas de double opt-in ni désinscription (à vérifier pour le RGPD). Export CSV côté propriétaire présent (`lib/csv.ts`).

### (d) Limites de projets par formule vérifiées côté serveur ?
- **Sites publiés (`maxSites`) : oui**, serveur. `api/sites` lit la formule dans `profiles` (colonne non modifiable par l'utilisateur : `update` limité à `favorites`) et refuse (403). Écriture directe dans `sites` interdite par `0002`. Webhook Stripe suspend les sites excédentaires.
- **Projets (`maxProjets`) : non**, navigateur seulement (`store.ts` `canCreateProject`). La table `projects` accepte tout insert d'un utilisateur connecté (RLS = propriétaire, taille limitée à 3 Mo/ligne seulement). Un utilisateur gratuit peut donc écrire des projets directement via l'API Supabase. Impact limité aujourd'hui (les projets ne coûtent presque rien et la publication, elle, est contrôlée), mais à corriger pour une plateforme : trigger SQL ou route serveur.
- Autres droits (`modelesPremium`, `exportFichiers`, `duplication`, `personnalisationAvancee`) : vérifiés dans l'interface (`can()` dans `plans.ts`) ; l'export se fait côté navigateur, donc non protégé côté serveur. Niveau 2.
- Note : la doc `docs/MISE-EN-LIGNE.md` dit « Gratuit : 1 projet (aperçu) » alors que `plans.ts` donne `maxProjets: 0`. Incohérence documentaire.
- Le plan local (sans Stripe) s'active à la main dans le navigateur : sans cloud, aucune limite réelle.

### (e) Chemin le plus sûr pour un premier modèle « Boutique » complet
1. Ne pas viser un SaaS multi-boutiques d'emblée. Premier jalon : **boutique publiée sur `/s/[slug]`, une par créateur**, avec produits en base et commande par **Stripe Checkout (paiement unique)** vers le compte du vendeur.
2. Schéma dédié (migration 0004, non destructive, RLS dès le départ, tests PGlite sur le modèle de `waitlist-rls.test.ts`) : `shop_products` (prix en centimes, stock, statut), `shop_orders`, `shop_order_items`, rattachées à `sites.slug`/`user_id`. Écriture des commandes uniquement par le serveur (service_role), lecture par le vendeur ; le prix est toujours relu côté serveur, jamais envoyé par le navigateur (même principe que `api/stripe/checkout`).
3. Étape 1 sans paiement en ligne : catalogue réel + commande « à régler à la livraison / virement » + e-mail au vendeur. Étape 2 : Stripe Connect (comptes connectés) ou, plus simple au début, clés Stripe du vendeur chiffrées. Décision à trancher : Décollage encaisse-t-il pour le vendeur (responsabilité, TVA, KYC) ? À valider avec un juriste.
4. Stock : décrément atomique en SQL (fonction `security definer` ou `update ... where stock >= qte`) pour éviter la survente ; webhook pour confirmer le paiement.
5. Réutiliser le prototype `co-products/co-orders` comme interface du vendeur, en branchant sa couche de données sur l'API au lieu de localStorage. Panier client en localStorage (acceptable), commande envoyée au serveur.
6. Prérequis de conformité : CGV du vendeur, mentions, rétractation 14 jours, e-mail de confirmation, politique de données des acheteurs ; limites par formule contrôlées côté serveur (corriger aussi `maxProjets`).
7. Tester avec Stripe en mode test, un seul modèle, quelques vendeurs pilotes, avant d'ouvrir à tous.

## 5. Risques et manques repérés
- `maxProjets` non appliqué côté serveur (voir d).
- Pas d'historique de versions de site ni de retour arrière ; pas de domaines personnalisés ; marque blanche non appliquée aux sites publiés.
- Limite anti-spam en mémoire (non partagée entre instances).
- Pas de tests automatisés sur le parcours Stripe réel ni sur l'interface (pas de tests de composants/E2E) ; une seule exécution live ignorée.
- État de la base de production inconnu (migrations 0001-0003 appliquées ou non) : à vérifier avant toute évolution (`loadSite` et `site-lifecycle` ont des replis si 0002 manque).
- Pas de journal d'audit/monitoring visible (seulement `console.error`).
